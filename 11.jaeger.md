# Jaeger — 分布式链路追踪

> **架构流程**：`Request → Ingress-Nginx → vLLM Router → Prefill/Decode → LMCache Server`
>
> Jaeger 追踪请求在以上组件之间的全链路调用，帮助定位延迟瓶颈、分析调用拓扑、排查异常请求。

---

## 1. 为什么需要链路追踪？

在 LLM 推理服务的微服务架构中，一个请求会经过多个组件：

```
客户端 → Ingress-Nginx → vLLM/SGLang Router → Prefill Pod → LMCache → Decode Pod
```

当出现以下问题时，缺少链路追踪将很难排查：

| 问题 | 无追踪 | 有追踪 |
|------|--------|--------|
| TTFT 突增 | 不知道是哪个环节慢 | 一眼看到 Prefill 还是 LMCache 网络延迟 |
| 请求超时 | 逐个 Pod 翻日志 | 按 Trace ID 搜索全链路 |
| 缓存命中率低 | 不知道哪些前缀没命中 | Span 中记录了 `cache_hit` 属性 |
| 扩缩容滞后 | 缺少请求级别延迟分布 | 可按 Trace 聚合 P95/P99 延迟 |

## 3. 组件说明

### 3.1 Jaeger

| 组件 | 端口 | 说明 |
|------|------|------|
| **Jaeger Collector** | 14250 (gRPC), 4317 (OTLP HTTP), 14268 (HTTP) | 接收 Span 数据 |
| **Jaeger Query** | 16686 (HTTP) | Web UI，查询和展示 Trace |
| **Storage** | — | in-memory（开发）/ Elasticsearch（生产） |

### 3.2 OpenTelemetry Collector

OTEL Collector 作为中间网关，统一接收所有服务的 Span，处理后转发给 Jaeger：

- **Receiver**：OTLP gRPC (4317) / OTLP HTTP (4318)
- **Processor**：batch（批量发送，降低网络开销）
- **Exporter**：Jaeger gRPC (14250)

### 3.3 应用端 Instrumentation

- **Python 服务（vLLM、SGLang、LMCache、Router）**：使用 `opentelemetry-distro` 自动注入 + 手动增强
- **Ingress-Nginx**：通过 `opentracing` 模块自动生成 Span，传播 Trace Context
- **Open-WebUI**：前端注入 `X-Trace-Id` 头

## 5. 部署步骤

### 5.1 安装 cert-manager

Jaeger Operator 通过 Webhook 验证 Jaeger CR，需要 cert-manager 管理证书。

```bash
# 添加 JetStack Helm 仓库
helm repo add jetstack https://charts.jetstack.io
helm repo update

# 下载
helm pull jetstack/cert-manager
tar -xf cert-manager-*.tgz
cd cert-manager/

# 安装
helm install cert-manager . \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true

# 验证
kubectl wait --for=condition=ready pod -l app.kubernetes.io/instance=cert-manager -n cert-manager --timeout=120s
kubectl get pods -n cert-manager
```

### 5.2 安装 Jaeger Operator

```bash
# 添加 Jaeger Tracing Helm 仓库
helm repo add jaegertracing https://jaegertracing.github.io/helm-charts
helm repo update

# 下载
helm pull jaegertracing/jaeger-operator
tar -xf jaeger-operator-*.tgz
cd jaeger-operator/

# 安装
helm install jaeger-operator . \
  --namespace observability \
  --create-namespace

# 验证 Operator 就绪
kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=jaeger-operator -n observability --timeout=120s
```

### 5.5 配置 Ingress-Nginx 链路追踪

Ingress-Nginx 支持通过 `opentracing` 模块将请求信息作为 Span 发送给 Jaeger。

修改 Ingress-Nginx 配置：

```bash
# 编辑 ConfigMap
kubectl edit configmap ingress-nginx-controller -n ingress-nginx
```

加入以下配置：

```yaml
data:
  # ========== OpenTracing / Jaeger 配置 ==========
  enable-opentracing: "true"
  jaeger-collector-host: "otel-collector.observability.svc.cluster.local"
  jaeger-collector-port: "4317"
  jaeger-service-name: "ingress-nginx"
  jaeger-sampler-type: "probabilistic"
  jaeger-sampler-param: "0.1"
  # 传播传入的 Trace Context（W3C TraceContext）
  opentracing-trust-incoming-span: "true"
  # 按比例采样（0.1 = 10%）
  jaeger-propagation-format: "w3c"
```

重启 Ingress Controller 使配置生效：

```bash
kubectl rollout restart deployment ingress-nginx-controller -n ingress-nginx
```

```bash
kubectl apply -f yaml/jaeger/04-jaeger-ingress.yaml
```

## 6. 应用端 Instrumentation

### 6.1 Python 服务自动注入（推荐）

使用 OpenTelemetry 的 `zero-code` 自动注入，无需修改代码：

#### 6.1.1 构建带 OTEL 的 vLLM 镜像

```dockerfile
# Dockerfile.vllm-otel
FROM vllm/vllm-openai:v0.11.2

# 安装 OpenTelemetry 分发版（自动注入 Flask/FastAPI/gRPC/Requests 等库）
RUN pip install --no-cache-dir \
    opentelemetry-distro \
    opentelemetry-exporter-otlp-proto-grpc \
    opentelemetry-instrumentation-fastapi \
    opentelemetry-instrumentation-grpc \
    opentelemetry-instrumentation-requests \
    opentelemetry-instrumentation-httpx
```

#### 6.1.2 自动注入 vs 程序化启动

**方式 A：`opentelemetry-instrument` 命令包装（零代码侵入）**

```bash
opentelemetry-instrument \
  --traces_exporter otlp \
  --exporter_otlp_endpoint http://otel-collector.observability.svc.cluster.local:4317 \
  --service_name vllm-prefill \
  python -m vllm.entrypoints.openai.api_server \
    /data/models/qwen3-0.6B \
    --served-model-name qwen3-06b \
    ...
```

**方式 B：InitContainer 注入 SDK（更灵活）**

参见 [6.3 节](#63-initcontainer-注入方式推荐) 的 InitContainer 方案。

### 6.2 手动增强关键 Span

自动注入覆盖网络调用（HTTP/gRPC），但业务关键节点需要手动添加 Span：

```python
# 在 vLLM Prefill 中手动记录关键阶段
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

@tracer.start_as_current_span("prefill.compute")
def process_prefill(prompt_tokens):
    # 给 Span 添加属性
    span = trace.get_current_span()
    span.set_attribute("prefill.batch_size", len(prompt_tokens))
    span.set_attribute("prefill.total_tokens", sum(len(p) for p in prompt_tokens))
    # ... 原有逻辑
```

### 6.3 InitContainer 注入方式（推荐）

为 Python 服务 Pod 添加 InitContainer，在容器启动前安装 OTEL 依赖并配置自动注入。

#### ConfigMap：OTEL 安装脚本

```bash
kubectl apply -f yaml/jaeger/05-otel-instrumentation-cm.yaml
```

#### vLLM StatefulSet 中添加 InitContainer

```yaml
initContainers:
# ========== OTEL 自动注入初始化 ==========
- name: otel-setup
  image: python:3.11-slim
  command:
  - sh
  - -c
  - |
    # 将 OTEL SDK 安装到共享 Volume
    pip install --target /otel-packages \
      opentelemetry-distro \
      opentelemetry-exporter-otlp-proto-grpc \
      opentelemetry-instrumentation-fastapi \
      opentelemetry-instrumentation-grpc \
      opentelemetry-instrumentation-requests \
      opentelemetry-instrumentation-logging 2>&1
    echo "OpenTelemetry packages installed"
  volumeMounts:
  - name: otel-packages
    mountPath: /otel-packages
  resources:
    limits:
      memory: "512Mi"
      cpu: "500m"
```

在主容器中：

```yaml
containers:
- name: vllm-prefill
  # 改用 opentelemetry-instrument 包装启动命令
  command: ["opentelemetry-instrument"]
  args:
    - --traces_exporter
    - otlp
    - --exporter_otlp_endpoint
    - http://otel-collector.observability.svc.cluster.local:4317
    - --service_name
    - vllm-prefill
    - --
    - python
    - -m
    - vllm.entrypoints.openai.api_server
    - /data/models/Qwen3-0.6B
    - --served-model-name
    - qwen3-06b
    # ... 其余 vLLM 参数
  env:
    - name: PYTHONPATH
      value: "/otel-packages:$(PYTHONPATH)"
    - name: OTEL_SERVICE_NAME
      value: "vllm-prefill"
    - name: OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://otel-collector.observability.svc.cluster.local:4317"
    - name: OTEL_RESOURCE_ATTRIBUTES
      value: "service.namespace=llm-inference,model=qwen3-06b"
    - name: OTEL_PROPAGATORS
      value: "tracecontext,baggage"
  volumeMounts:
    - name: otel-packages
      mountPath: /otel-packages
    - name: host-model-cache
      mountPath: /data/models
      readOnly: true
```

### 6.4 Open-WebUI 传播 Trace ID

Open-WebUI 前端可以生成并传播 Trace ID：

```yaml
# open-webui-deployment.yaml 中添加环境变量
env:
  # OpenTelemetry 后端地址（如果 Open-WebUI 支持 OTEL）
  - name: OTEL_EXPORTER_OTLP_ENDPOINT
    value: "http://otel-collector.observability.svc.cluster.local:4317"
  - name: OTEL_SERVICE_NAME
    value: "open-webui"
```

> **提示**：如果 Open-WebUI 本身的 OTEL 支持不完善，可以至少确保它透传 `X-Trace-Id` 请求头，便于在 Ingress 层关联前端请求与后端 Trace。

## 7. 采样策略

### 7.1 采样模式对比

| 模式 | 配置 | 适用场景 |
|------|------|---------|
| **全量采样** | `sampler.type: const, sampler.param: 1` | 开发/调试 |
| **概率采样** | `sampler.type: probabilistic, sampler.param: 0.1` | 生产环境 10% |
| **自适应采样** | `sampler.type: remote` | 生产环境，按 QPS 动态调整 |
| **基于错误采样** | `sampler.type: parentbased_traceidratio` | 错误请求 100% 采样 |

### 7.2 推荐配置

**开发环境**：全量采样（便于调试）

```yaml
# Jaeger CR 中配置
sampling:
  options:
    default_strategy:
      type: probabilistic
      param: 1.0
```

**生产环境**：分级采样

```
Ingress → 100% 生成 Trace（轻量 Span）
   ├── /health, /metrics → 丢弃（不采样）
   ├── /v1/chat/completions → 10% 采样
   └── error (5xx) → 100% 采样
```

通过 OTEL Collector 的 `probabilistic_sampler` 和 `tail_sampling` 处理器实现：

```yaml
# otel-collector 配置
processors:
  probabilistic_sampler:
    sampling_percentage: 10
  tail_sampling:
    policies:
      - name: errors-only
        type: status_code
        status_code: { status_codes: [ERROR] }
      - name: latency-over-5s
        type: latency
        latency: { threshold_ms: 5000 }
```

## 8. 查看 Trace

### 8.1 Jaeger UI

浏览器访问 `http://jaeger.demo.com`（或通过 `kubectl port-forward`）：

```bash
kubectl port-forward -n observability svc/jaeger-query 16686:16686
```

常用操作：

```
1. Service 下拉栏选择服务（如 vllm-prefill、vllm-decode、ingress-nginx）
2. Operation 选择接口（如 /v1/chat/completions）
3. 点击 Find Traces 查看 Trace 列表
4. 选择一条 Trace 查看完整调用链：
   ├── ingress-nginx          (12ms)   ← 网关层延迟
   │   └── vllm-router        (8ms)    ← 路由调度
   │       ├── vllm-prefill    (320ms)  ← Prefill 计算
   │       │   └── lmcache-server (5ms) ← KV Cache 写入
   │       └── vllm-decode     (1800ms) ← Decode 逐 token 生成
   │           └── lmcache-server (3ms) ← KV Cache 读取
```

### 8.2 关键指标与 Trace 关联

Jaeger UI 中点击某个 Span，查看 **Tags** 标签页：

| Tag Key | 示例值 | 含义 |
|---------|--------|------|
| `model.name` | `qwen3-06b` | 模型名称 |
| `request.tokens` | `512` | 输入 token 数 |
| `response.tokens` | `256` | 输出 token 数 |
| `cache.prefix_hit` | `true` | 是否命中 prefix cache |
| `kv.role` | `kv_producer` | Prefill/Decode 角色 |
| `session.id` | `abc123` | 用户会话 ID |
| `http.status_code` | `200` | HTTP 状态码 |

## 9. 示例：完整链路

下面是一条典型的 LLM 推理请求在 Jaeger 中的完整 Trace：

```
Service                  Operation                        Duration
─────────────────────────────────────────────────────────────────
ingress-nginx            /v1/chat/completions            2,340ms
 └─ vllm-router          route_request                    2,310ms
     ├─ vllm-prefill     prefill.compute                   320ms
     │   ├─ prefill.attention                           180ms
     │   ├─ prefill.mlp                                 110ms
     │   └─ lmcache.write_kv                              5ms
     └─ vllm-decode      decode.generate                1,980ms
         ├─ decode.sample.token.1                          18ms
         ├─ decode.sample.token.2                          15ms
         ├─ ... (逐 token 生成，共 128 tokens)
         ├─ decode.sample.token.128                        14ms
         └─ lmcache.read_kv                                3ms
```

从这个 Trace 可以快速定位：
- **TTFT 瓶颈**：Prefill 阶段 320ms，主要时间在 attention 计算
- **总延迟瓶颈**：Decode 阶段 1,980ms（128 tokens × ~15ms/token）
- **缓存延迟**：LMCache 读写各 3-5ms，网络正常

## 12. 故障排查

### 12.1 Jaeger UI 中看不到 Traces

```bash
# 1. 确认 OTEL Collector 正在接收 Span
kubectl logs -n observability deployment/otel-collector | grep "TracesExporter"
# 如果没有输出，说明 Span 没有到达 Collector

# 2. 检查 Collector → Jaeger 连通性
kubectl exec -n observability deployment/otel-collector -- \
  nc -zv jaeger-collector.observability.svc.cluster.local 14250

# 3. 检查应用端 OTEL 配置
kubectl logs -n llm-inference vllm-prefill-0 | grep -i "otel\|trace"
```

### 12.2 Ingress Span 缺失

```bash
# 确认 ConfigMap 已生效
kubectl get configmap ingress-nginx-controller -n ingress-nginx -o yaml | grep -A5 opentracing

# 确认 Ingress Controller 已重启并加载新配置
kubectl rollout status deployment ingress-nginx-controller -n ingress-nginx

# 查看 Nginx 日志
kubectl logs -n ingress-nginx deployment/ingress-nginx-controller | grep -i "jaeger\|opentracing"
```

### 12.3 内存占用过高

```bash
# 降低采样率（OTEL Collector ConfigMap）
processors:
  probabilistic_sampler:
    sampling_percentage: 1   # 从 10% 降到 1%

# 减少 Jaeger 内存限制
# 编辑 Jaeger CR:
spec:
  allInOne:
    resources:
      limits:
        memory: "2Gi"  # 从默认值减少
```

## 13. 生产环境建议

1. **存储升级**：从 `allInOne`（内存）切换到 `production` 模式 + Elasticsearch 持久化存储
2. **采样策略**：生产环境使用 tail-based sampling（基于延迟/错误采样），保留全量错误 Trace
3. **数据保留**：Elasticsearch 配置索引生命周期（ILM），自动清理过期 Trace（如保留 7 天）
4. **Span 过滤**：OTEL Collector 中过滤 `/health`、`/metrics` 端点的 Span，减少噪音
5. **与 Prometheus 联动**：通过 Exemplar 将 Trace ID 写入 Prometheus 指标，从监控图表一键跳转到 Trace
6. **日志关联**：将 Trace ID 注入应用日志，实现 `日志 ⇄ Trace` 双向跳转
